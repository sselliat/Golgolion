# 커밋과 브랜치

이 문서는 커밋 또는 브랜치를 생성, 수정하거나 정리할 때 적용한다.

## 커밋 단위

- PR 내부에서는 설정, 기능, 테스트, 문서처럼 독립적으로 설명할 수 있는 변경을
  논리적인 커밋으로 나눈다.
- 하나의 커밋에는 하나의 논리적으로 완결된 변경만 포함한다.
- 기능 구현, 해당 테스트 및 해당 문서 갱신은 같은 목적이면 한 커밋에 포함할 수
  있다.
- 관련 없는 리팩터링이나 포맷 변경을 같은 커밋에 섞지 않는다.
- 커밋 시점에는 해당 범위가 빌드되거나 검증 가능한 상태여야 한다.
- 작업 브랜치의 임시 `WIP` 또는 수정 커밋은 merge 전 squash로 정리한다.
- 사용자의 기존 커밋을 임의로 amend하거나 재작성하지 않는다.
- 파일 수나 변경 줄 수만으로 커밋을 나누지 않는다.

## 커밋 메시지

Conventional Commits 형식을 사용한다.

```text
<type>[(optional-scope)]: <한글 설명>

[선택적인 본문]

[선택적인 footer]
```

다음 type을 사용한다.

- `feat`: 사용자 또는 시스템 기능 추가
- `fix`: 결함 수정
- `docs`: 문서만 변경
- `test`: 테스트만 추가 또는 수정
- `refactor`: 동작 변경 없는 코드 구조 개선
- `perf`: 성능 개선
- `build`: 빌드 또는 의존성 관련 변경
- `ci`: CI 설정 변경
- `chore`: 다른 분류에 속하지 않는 유지보수
- `revert`: 이전 변경 되돌리기

- 가장 구체적인 type을 사용하고 편의상 모든 변경을 `chore`로 분류하지 않는다.
- scope는 선택 사항이며 기능이나 영역을 `kebab-case`로 작성한다.
- 파일명 자체를 scope로 사용하지 않는다.
- type과 scope는 영문으로 작성한다.
- 제목 설명과 본문은 한글로 작성한다.
- 제목은 변경 결과를 간결하게 설명하고 끝에 마침표를 붙이지 않는다.
- `수정`, `업데이트`, `작업`만 적지 않고 무엇이 달라졌는지 명시한다.
- diff로 알 수 없는 이유나 제약이 있을 때만 본문을 작성한다.
- 본문에는 구현 목록보다 변경 이유와 중요한 트레이드오프를 기록한다.
- 호환성을 깨는 변경은 type 또는 scope 뒤에 `!`를 붙이고 본문에 영향과
  마이그레이션 방법을 기록한다.
- 이슈를 참고하는 커밋 footer에는 `Refs: #번호`를 사용할 수 있다.

```text
feat(market-price): 현재가 대표 가격군 계산 추가
fix(collector): 수집 복구 후 연속성 판정 수정
docs: 코드 컨벤션 문서 추가
test(ohlc): 한국 시간 날짜 경계 사례 추가
```

```text
fix(collector): 무거래와 수집 실패 상태를 분리

수집 실패를 빈 체결 응답으로 취급하면 정상적인 무거래와
데이터 누락을 구분할 수 없어 상태 판정을 분리한다.

Refs: #15
```

## 브랜치

- 브랜치명은 가능하면 `<type>/<issue-number>-<short-description>` 형식을 사용한다.
- 브랜치 설명은 짧은 영문 `kebab-case`로 작성한다.
- Orca 등 작업 도구가 브랜치명을 관리하면 도구가 생성한 이름을 유지한다.
- 공유 브랜치에 force push하지 않는다.
- PR merge 후 더 이상 필요하지 않은 작업 브랜치는 삭제한다.

```text
docs/4-code-conventions
fix/15-collector-continuity
```
