# 기여 규칙

커밋, 브랜치, 이슈, Pull Request 및 merge에 적용한다. 코드 작성 규칙은
[코드 컨벤션](CODE_CONVENTIONS.md)을 따른다.

## 커밋 단위

- 하나의 커밋에는 하나의 논리적으로 완결된 변경만 포함한다.
- 기능 구현, 해당 테스트 및 해당 문서 갱신은 같은 목적이면 한 커밋에 포함할 수 있다.
- 관련 없는 리팩터링이나 포맷 변경을 같은 커밋에 섞지 않는다.
- 커밋 시점에는 해당 범위가 빌드되거나 검증 가능한 상태여야 한다.
- 작업 브랜치의 임시 `WIP` 또는 수정 커밋은 merge 전 squash로 정리한다.
- 사용자의 기존 커밋을 임의로 amend하거나 재작성하지 않는다.
- 특정 변경 줄 수를 기준으로 커밋을 나누지 않는다.

## 커밋 메시지

Conventional Commits 형식을 사용한다.

```text
<type>[(optional-scope)]: <한글 설명>

[선택적인 본문]

[선택적인 footer]
```

다음 type을 사용한다.

- `feat`: 사용자 또는 시스템 기능 추가
- `fix`: 결함 수정
- `docs`: 문서만 변경
- `test`: 테스트만 추가 또는 수정
- `refactor`: 동작 변경 없는 코드 구조 개선
- `perf`: 성능 개선
- `build`: 빌드 또는 의존성 관련 변경
- `ci`: CI 설정 변경
- `chore`: 다른 분류에 속하지 않는 유지보수
- `revert`: 이전 변경 되돌리기

- 가장 구체적인 type을 사용하고 편의상 모든 변경을 `chore`로 분류하지 않는다.
- scope는 선택 사항이며 기능이나 영역을 `kebab-case`로 작성한다.
- 파일명 자체를 scope로 사용하지 않는다.
- type과 scope는 영문으로 작성한다.
- 제목 설명과 본문은 한글로 작성한다.
- 제목은 변경 결과를 간결하게 설명하고 끝에 마침표를 붙이지 않는다.
- `수정`, `업데이트`, `작업`만 적지 않고 무엇이 달라졌는지 명시한다.
- diff로 알 수 없는 이유나 제약이 있을 때만 본문을 작성한다.
- 본문에는 구현 목록보다 변경 이유와 중요한 트레이드오프를 기록한다.
- 호환성을 깨는 변경은 type 또는 scope 뒤에 `!`를 붙이고 본문에 영향과 마이그레이션 방법을 기록한다.
- 이슈를 참고하는 커밋 footer에는 `Refs: #번호`를 사용할 수 있다.

```text
feat(market-price): 현재가 대표 가격군 계산 추가
fix(collector): 수집 복구 후 연속성 판정 수정
docs: 코드 컨벤션 문서 추가
test(ohlc): 한국 시간 날짜 경계 사례 추가
```

```text
fix(collector): 무거래와 수집 실패 상태를 분리

수집 실패를 빈 체결 응답으로 취급하면 정상적인 무거래와
데이터 누락을 구분할 수 없어 상태 판정을 분리한다.

Refs: #15
```

## 브랜치와 PR 범위

- 하나의 PR은 하나의 이슈 또는 하나의 논리적 목적만 처리한다.
- PR에서 요청 범위를 임의로 확대하지 않는다.
- 관련 없는 발견 사항은 별도 이슈로 분리한다.
- 큰 작업은 구현 전에 독립적으로 검증 가능한 하위 이슈로 나눈다.
- 브랜치명은 가능하면 `<type>/<issue-number>-<short-description>` 형식을 사용한다.
- 브랜치 설명은 짧은 영문 `kebab-case`로 작성한다.
- Orca 등 작업 도구가 브랜치명을 관리하면 도구가 생성한 이름을 유지한다.
- 공유 브랜치에 force push하지 않는다.
- PR merge 후 더 이상 필요하지 않은 작업 브랜치는 삭제한다.

```text
docs/4-code-conventions
fix/15-collector-continuity
```

## PR 제목과 본문

- PR 제목은 Conventional Commits 형식을 사용한다.
- PR 제목의 type과 선택적 scope는 영문, 설명은 한글로 작성한다.
- PR 본문은 한글로 작성한다.
- PR 본문에는 개요, 주요 변경 사항, 검증, 영향 및 관련 이슈를 포함한다.
- UI가 변경되면 데스크톱과 모바일 스크린샷 또는 짧은 영상을 추가한다.
- 데이터 계약이나 마이그레이션이 변경되면 변경 전후 형태와 운영 영향을 설명한다.

```markdown
## 개요

변경 목적과 배경

## 주요 변경 사항

- 핵심 변경
- 중요한 설계 결정

## 검증

- `npm test`
- `npm run build`
- 실행하지 못한 검증과 이유

## 영향

사용자 화면, API, 데이터, 배포 또는 호환성 영향

## 관련 이슈

Closes #4
```

## 이슈 연결

- PR이 이슈의 완료 조건 전체를 충족하면 `Closes #번호`를 사용한다.
- 이슈의 일부만 처리하거나 후속 작업이 남으면 `Refs #번호`를 사용한다.
- 여러 이슈를 닫을 때는 각 이슈에 closing keyword를 작성한다.
- PR 제목에만 이슈 번호를 적고 본문 연결을 생략하지 않는다.
- 실제로 완료하지 않은 이슈에 closing keyword를 사용하지 않는다.
- 이슈 종료는 개별 커밋보다 PR 본문에서 관리한다.

## Draft와 검증

- 구현 또는 필수 검증이 남아 있으면 Draft PR로 생성한다.
- 요구사항과 완료 조건을 충족하고 관련 검증을 통과한 후 Ready for review로 전환한다.
- 검증 항목에는 실제로 실행한 명령과 결과만 기록한다.
- 실행하지 않은 테스트를 실행한 것처럼 표시하지 않는다.
- 실행하지 못한 검증은 이유와 남은 위험을 명시한다.
- 문서만 변경한 경우 런타임 테스트를 생략할 수 있지만 diff, 링크 및 Markdown 검증 결과를 기록한다.
- UI 변경은 데스크톱과 모바일에서 확인한다.
- API 또는 데이터베이스 변경은 계약, 오류 및 마이그레이션 시나리오를 확인한다.
- 비밀값, fixture의 식별 정보 및 불필요한 생성 파일이 diff에 없는지 확인한다.
- 검토 중 발견한 범위 밖 문제는 별도 이슈로 기록한다.

## merge

- PR은 squash 방식으로 merge한다.
- 완료 조건과 필수 검증을 모두 충족한 후 merge한다.
- unresolved review thread가 없어야 한다.
- PR 본문을 최종 변경 사항과 검증 결과에 맞게 갱신한다.
- 범위 밖 변경이 없어야 한다.
- squash 커밋 제목이 Conventional Commits 형식인지 확인한다.
