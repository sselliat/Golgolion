# 협업 워크플로

## 핵심 원칙

모호한 목표, 에픽, 프로젝트 요청 또는 아키텍처 요청은 구현 작업이 아니다.

짧은 이슈 제목만 보고 명시되지 않은 기술을 임의로 선택하거나 프로젝트를 초기화해도 된다고 해석하지 않는다.

## 계획 요청

다음 조건 중 하나라도 해당하면 해당 이슈를 계획 요청으로 취급한다.

- `kind:goal`, `phase:discovery` 또는 `agent:plan-only` 라벨이 지정되어 있다.
- 명시적인 인수 조건이 없다.
- 중요한 기술적 결정 사항이 정해지지 않았다.
- 하나의 작은 코드 변경이 아니라 달성하려는 결과를 설명하고 있다.

계획 요청인 경우 다음 작업을 수행하지 않는다.

- 저장소 파일을 생성, 수정, 이름 변경 또는 삭제하지 않는다.
- 프레임워크를 초기화하거나 의존성을 설치하지 않는다.
- 프로젝트 생성 도구를 실행하지 않는다.
- 커밋, 브랜치 또는 풀 리퀘스트를 생성하지 않는다.
- 명시적인 승인 없이 언어, 스타일링 방식, 패키지 관리자, 데이터베이스, 테스트 프레임워크, 디렉터리 구조 또는 배포 플랫폼을 선택하지 않는다.

먼저 다음 작업을 수행한다.

- 목표와 현재 이해한 내용을 다시 정리한다.
- 가정한 사항과 아직 결정되지 않은 사항을 나열한다.
- 영향도가 높은 질문을 소수의 묶음으로 제시한다.
- 실행 가능한 선택지와 각 선택지의 장단점을 제시한다.
- 권장안을 제시하되, 해당 권장안이 승인된 것으로 간주하지 않는다.
- 하나의 워크트리와 하나의 풀 리퀘스트로 처리할 수 있을 만큼 작은 GitHub 하위 이슈를 제안한다.
- 작업을 중단하고 명시적인 승인을 기다린다.

## 승인 게이트

다음 조건 중 하나를 충족한 경우에만 구현을 시작할 수 있다.

- 이슈에 `ready-for-agent` 라벨이 지정되어 있다.
- 사용자가 정확히 `APPROVED FOR IMPLEMENTATION`이라고 작성한다.

계획에 대한 승인은 해당 계획과 관련 없는 선택 사항까지 승인한 것으로 간주하지 않는다.

## 구현 작업

다음 조건을 모두 충족하는 최하위 단계의 이슈만 구현한다.

- 작업 범위가 명확하게 정의되어 있다.
- 명시적인 인수 조건이 있다.
- 관련 기술적 결정 사항이 정해져 있다.
- 검증 방법이 명시되어 있다.
- 해결되지 않은 차단 질문이 없다.

한 번에 하나의 이슈만 작업한다.

여러 개의 독립적으로 검증 가능한 결과를 포함한 상위 이슈는 진행 상황을 추적하는
용도로만 사용하고 직접 구현하지 않는다.

상위 이슈에는 `ready-for-agent` 라벨을 지정하지 않는다. 구현 가능한 최하위 하위
이슈에만 `ready-for-agent` 라벨을 지정한다.

하나의 하위 이슈는 하나의 PR로 처리한다. 해당 PR을 생성한 뒤 작업을 중단하고
사용자의 리뷰와 merge를 기다린다. 별도 요청 없이 다음 하위 이슈를 연속해서
구현하지 않는다.

먼저 묻지 않고 작업 범위를 확장하지 않는다.

## 코드 컨벤션

코드를 작성하거나 수정하는 작업을 수행할 때만 `docs/CODE_CONVENTIONS.md`를 먼저 읽고
준수한다. 해당 문서의 작업별 선택표에 따라 현재 작업과 관련된 세부 컨벤션 문서만
추가로 읽는다.

커밋, 브랜치, Pull Request 또는 merge만 수행하는 작업에는
`docs/CONTRIBUTING.md`만 읽고 준수한다.

단순 조사, 계획, 이슈 작성처럼 코드를 작성하거나 수정하지 않는 작업에는 해당 문서의 참조를 요구하지 않는다.
